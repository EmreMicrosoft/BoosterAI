# Functional partials workflow

First apply the project-workspace reference, including record-system selection. On a coding request, create or reuse `<project-root>/_partials/README.md` and `_partials/` within the authorized project. `python scripts/booster.py partials-init --root PROJECT` creates the scaffold; it preserves an existing index unchanged. Inspect and extend existing entries yourself without overwriting history or another active owner. If the earlier `_boosterAI/_partials/` exists, report and inspect it in place, preserving its history and avoiding duplicate implementations; do not move it or silently replace an existing root index. Initialization is not algorithm generation, implementation or verification.

## Decompose and execute
1. Read the project goal, current code, actual owners and algorithm. Update that algorithm from the request; reuse its canonical location. Do not duplicate the backlog in the partials index.
2. Choose the first smallest independent, independently invocable function that advances the actual goal. Describe inputs, outputs/effects, prerequisites, dependencies, target, acceptance and failure/recovery. If a prerequisite must be created by the product, implement and verify that prerequisite first.
3. Choose language in this exact order: explicit user request, existing module language, otherwise Python. No mandatory framework or external runtime package is introduced. TensorFlow or any other third-party library is not required by BoosterAI. A target project's existing dependencies remain explicit target prerequisites.
4. Put the function in its own short, descriptive source file under the project-root `_partials/`, with a stable unique suffix, stable interface and no secret test values. For example, a Python module may use `normalize_text_b73e19a2.py`; check that the suffix is not already used for another piece. For each function, add a detailed docstring or immediately preceding comment explaining its purpose, inputs, result, preconditions and side effects or failures where applicable. Do not rename or move existing working code or violate compilation/package rules merely to satisfy this convention. For existing code that must remain at its original path, use a small independent adapter or code fragment under `_partials/` and link its product location, documenting the exception. Do not create two divergent production implementations.
5. Invoke the function in its actual runtime/target using the real intended interface. Store or link evidence bound to its revision and target. Update the index with function/contract, file, dependencies, ownership/run, target/revision, evidence status, integration state and optional backup status.
6. Only after real acceptance, proceed to the next dependent function. Failed or unavailable execution remains FAIL or NOT_RUN. A mock service, generated screenshot, unit test alone or a green build is not a substitute for a missing real target. Diagnose or perform independent authorized work without pretending the gate passed.

## Product-owned integration and maintenance
The project consuming verified partials or archived code owns any combination needed at its established product interfaces. The skill does not undertake automatic merging, integration or subsequent refactoring. If the project combines pieces, verify the resulting behavior in its real target; verified fragments alone do not establish a verified whole. Preserve useful partials and index references; never garbage-collect source or acceptance evidence as temp.

When requests change, revise affected nodes/contracts and mark affected partial evidence stale until retested; leave unaffected verified parts intact. Index states should distinguish PLANNED, ACTIVE, NOT_RUN, FAIL, AMBIGUOUS, VERIFIED, INTEGRATED and STALE. A function can be individually VERIFIED while integration is still NOT_RUN.

## Optional per-step backup
Only if the user requests it and identifies/authorizes the destination and scope, back up each verified step to GitHub using the host's supported existing path. Review the diff for secrets and unrelated data; do not publish private code to a public destination without authorization. Record verified remote branch/commit readback, not just local commit or command exit. If unavailable/rejected, record BACKUP_FAILED with the actual reason and preserve local work. Continue independent authorized work unless the user's instructions make successful backup a prerequisite. No GitHub SDK, remote account or network is required for the core workflow, and the scaffold never performs a push automatically.
